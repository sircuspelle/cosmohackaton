# Events module

## Inception

Модуль `events` предназначен для автоматизированного сбора, нормализации и анализа данных о космической погоде и орбитальной обстановке. Основная цель — оценка возможных рисков для внекорабельной деятельности (ВКД) и других космических операций на основе разрозненных внешних источников.

### Входные данные

Модуль обрабатывает два типа входных данных:
1. **Параметры пользователя (Query)**:
   * **Временные рамки**: `start` (целевое начало, ISO 8601), `duration_hours` (длительность операции), `search_hours` (горизонт поиска подходящего окна), `step_minutes` (шаг смещения окна).
   * **Режимы (`mode`)**: `live` (оценка текущей ситуации), `reconstruction` (исторический срез), `as_of` (воспроизведение строго по кешу на заданный момент времени).
2. **Внешние телеметрические и каталожные данные**:
   * **JSON-источники**: NASA DONKI (каталоги событий FLR, SEP, CME и др., прогнозы WSA-Enlil), NOAA SWPC (наблюдения и прогнозы Kp-индекса, потоки протонов, рентгеновское излучение, текстовые алерты), NASA JPL (база CAD по сближениям с околоземными объектами).
   * **CSV-источники**: CelesTrak SOCRATES (данные о сближениях отслеживаемого космического мусора и спутников с МКС).

### Классификация обрабатываемых событий

Модуль распознаёт, нормализует и распределяет космические события по пяти физическим механизмам воздействия:

1. **Радиация (Radiation)**
   * `solar_particle_event` (SEP) — Солнечные протонные события (каталог DONKI).
   * `radiation_belt_enhancement` (RBE) — Усиления радиационных поясов Земли (каталог DONKI).
   * `radiation_threshold_episode` — Расчётные эпизоды превышения радиационного фона по данным спутников GOES (поток протонов ≥ 10 MeV превышает 10 pfu).
2. **Геомагнитные возмущения (Geomagnetic)**
   * `cme_observed_at_sun` (CME) — Корональные выбросы массы, зафиксированные на Солнце (DONKI).
   * `cme_arrival_forecast` — Внешние расчётные прогнозы прибытия CME к Земле (WSA-Enlil Simulations).
   * `geomagnetic_storm` (GST) — Геомагнитные бури (каталог DONKI).
   * `interplanetary_shock` (IPS) — Межпланетные ударные волны (каталог DONKI).
   * `high_speed_stream` (HSS) — Высокоскоростные потоки солнечного ветра (каталог DONKI).
   * `magnetopause_crossing` (MPC) — Пересечения магнитопаузы (каталог DONKI).
   * `geomagnetic_threshold_interval` — Трёхчасовые интервалы, в которых наблюдаемый или прогнозируемый Kp-индекс достигает порогового значения (по умолчанию ≥ 5) (данные NOAA).
3. **Помехи связи (Communications)**
   * `solar_flare` (FLR) — Солнечные вспышки с классификацией (каталог DONKI).
   * `xray_threshold_episode` — Расчётные эпизоды рентгеновских вспышек по данным спутников GOES (поток в канале 0.1–0.8 нм превышает 10⁻⁵ W/m², класс M и выше).
4. **Отслеживаемый мусор (Tracked Debris)**
   * `conjunction` — Опасные сближения (TCA — Time of Closest Approach) Международной космической станции (NORAD ID 25544) с другими отслеживаемыми объектами и космическим мусором (по данным CelesTrak SOCRATES).
5. **Метеороиды (Meteoroids)**
   * Модуль резервирует этот механизм в модели данных, однако в текущей версии прямые события метеороидных потоков не рассчитываются из-за отсутствия подходящего оперативного источника (отмечается как `model_required`).

**Контекстные события (Context):**
Некоторые события собираются исключительно для контекста аналитика и не блокируют ВКД автоматически:
* `close_approach` (CAD) — Сближения Земли с астероидами и кометами (данные NASA JPL).
* Текстовые предупреждения и алерты от NOAA SWPC (парсятся с извлечением времени публикации и отмены).

### источники данных

Ключи для используемых адресов не нужны. Доступность и ограничения поставщиков могут меняться. Четыре параллельных запроса, таймаут, ограниченные повторы, TTL-кеш; нет агрессивного бесконечного опроса. JPL вызывается один раз на расчёт до кеширования. Автообновление выполняется при обращении клиента после TTL; периодический фоновый сбор не реализован. Для регулярного архива вызывайте CLI планировщиком своей системы.

| Источник | Продукты | Использование |
|---|---|---|
| NOAA SWPC | Прогноз/наблюдения Kp | Трёхчасовые интервалы с Kp ≥ 5 |
| NOAA GOES primary | Протоны ≥10 MeV | Эпизоды превышения 10 pfu |
| NOAA GOES primary | Рентген 0.1–0.8 nm | Эпизоды превышения 10⁻⁵ W/m² |
| NOAA SWPC | Alerts | Оригинальные сообщения и распознанные времена для проверки аналитиком |
| NASA DONKI | FLR, SEP, CME, GST, IPS, HSS, RBE, MPC | Каталоги событий, связи и версии |
| NASA DONKI | WSAEnlilSimulations | Внешние прогнозы прихода CME к Земле |
| CelesTrak | Полный SOCRATES CSV | Сближения, в которых один из объектов — NORAD 25544 |
| NASA JPL | CAD | Астероиды/кометы возле Земли, только контекст |

### Выходные данные

В качестве результата модуль предоставляет детальную оценку обстановки, разбитую на дискретные временные окна (кандидаты для проведения операции). Для каждого окна формируется сводка выявленных угроз по пяти физическим механизмам: радиация (`radiation`), геомагнитные возмущения (`geomagnetic`), помехи связи (`communications`), столкновения с отслеживаемым мусором (`tracked_debris`) и метеороидами (`meteoroids`).

### Формат выходных данных

Выходные данные возвращаются строго в формате **JSON** (в теле HTTP-ответа REST API или сохраняются в файл при вызове CLI). 
Структура корневого объекта JSON:

* `query` и `configuration` — эхо применённых параметров запроса и пороговых настроек из конфига.
* `recommendation` — сводный вердикт. Включает `status` (например, `insufficient_evidence`, `go` и т.д.) и `preferred_window` (рекомендуемое окно, если найдено безопасное).
* `windows` — массив оценённых временных интервалов. Каждый элемент содержит:
  * Границы окна `start` и `end` (ISO 8601).
  * `factors` — подробная оценка по каждому из 5 механизмов воздействия. Содержит метрики: продолжительность перекрытия с опасным явлением в минутах (`known_interval_overlap_minutes`), количество событий (`event_count`), статус безопасности механизма, минимальная дистанция пролёта (`minimum_miss_distance_km`) и т.д.
* `events` — массив всех релевантных событий (вспышки, пролёты мусора, геомагнитные штормы), нормализованных к единому стандарту: `id`, `mechanism`, `kind`, временные рамки (`start`, `end`) и привязка к источнику.
* `context` — массив сопутствующей информации (например, оригинальные текстовые алерты NOAA или пролёты далёких астероидов), не влияющей на автоматические блокировки, но доступной для аналитика.
* `sources` — метаданные опрошенных провайдеров: статус сети (`fresh`, `stale`, `unavailable`), метки времени загрузки (`fetched_at`) и ID снимков в кеше.
* `limitations` — строковый массив с перечнем допущений и архитектурных ограничений текущего расчёта.
* `run_id` — уникальный идентификатор сохранённого отчёта в базе SQLite.

Каждое окно содержит `factors` по механизмам `radiation`, `geomagnetic`, `communications`, `tracked_debris`, `meteoroids`.

| Поле | Значение |
|---|---|
| `event_count` | Количество записей событий, затрагивающих окно. Не число независимых опасностей. |
| `event_types` | Категории событий и количество записей каждого типа. |
| `linked_group_count` | Число групп по явным связям каталога; не доказательство независимости групп. |
| `known_interval_overlap_minutes` | Длина объединения заданных интервалов внутри окна. Наблюдения, прогнозы и расчётные интервалы могут пересекаться. |
| `observation_overlap_minutes` | Пересечение с интервалами событий из наблюдательного каталога. |
| `external_forecast_overlap_minutes` | Пересечение с интервалами внешнего прогноза. |
| `team_calculation_overlap_minutes` | Пересечение с рассчитанными пороговыми эпизодами GOES. |
| `possible_ongoing_event_ids` | События без известного окончания: продолжение возможно, длительность не установлена. |
| `next_event_in_minutes` | Время от начала окна до ближайшего известного начала; поиск ограничен загруженным набором. |
| `coverage_fraction` | Покрытие окна выбранными продуктами. Это НЕ доля знания обо всём механизме воздействия. |
| `source_max_age_minutes` | Максимальная давность получения выбранных записей; не возраст самого события. |
| `minimum_miss_distance_km` | Минимальная дистанция сближения МКС среди событий окна. |
| `maximum_relative_speed_km_s` | Максимальная относительная скорость среди таких событий. |
| `status` | Выявленные события, недостаток данных или оба условия. |

## Elaboration

### Архитектура приложения

Проект организован в соответствии со строгой модульной структурой, разделяющей исходный код, тесты, данные и конфигурации:

*   **`src/main/events/`** — Основной исходный код приложения:
    *   `app.py` — Точка входа для CLI и HTTP REST API (эндпоинты `/assess`, `/health`, `/runs`, `/snapshots`). Отвечает за маршрутизацию, запуск веб-сервера (`ThreadingHTTPServer`) и базовую валидацию форматов ввода.
    *   `service.py` — Оркестратор бизнес-логики (`run`, `collect`, `config_load`). Управляет параллельным сбором данных (`ThreadPoolExecutor`), фильтрует отключенные источники и связывает слой данных с ядром расчётов.
    *   `core.py` — Чистая логика предметной области (без I/O операций). Выполняет оценку окон (`assess`), нормализацию времени (`dt`, `iso`), вычисление пересечений интервалов (`union_minutes`) и проверку ограничений запроса (`validate_query`).
    *   `adapters.py` — Слой абстракции поставщиков данных. Содержит парсеры (`goes`, `donki`, `socrates`, `alerts` и др.), которые преобразуют сырые специфичные форматы (JSON/CSV) в универсальные `event` и `context` объекты.
    *   `storage.py` — Менеджер кеша и истории (`Store`). Выполняет сетевые запросы (`urlopen`), поддерживает TTL-кеширование неизменяемых снимков, режим `offline`, а также сохраняет результаты расчётов в БД SQLite.
    *   `demo.py` — Генератор синтетических данных (`make_demo`) для демонстрации возможностей без сети.
*   **`src/test/events/`** — Модульные и интеграционные тесты (`test_service.py`, `test_extended.py`), использующие `unittest`.
*   **`config/events/`** — Директория конфигурационных файлов (например, `config.example.json`), хранящая пороги значимости событий и настройки тайм-аутов.
*   **`data/events/`** — Файлы данных. Здесь располагается база данных SQLite (`eva.sqlite3`), хранящая снимки ответов (snapshots) и историю запусков (runs).
*   **`docs/events/`** — Документация проекта, включая этот файл, описания феноменов (`PHENOMENA.md`) и правила валидации (`VALIDATION.md`).

## Construction

### механизм реализации

Проект реализован на Python 3.10 без использования сторонних зависимостей (отсутствуют `requests`, `pandas` и прочие внешние библиотеки)

Ключевые технические решения:
1. **Сетевое взаимодействие**: Выполняется встроенной библиотекой `urllib.request`. Для ускорения работы применяется параллельный опрос источников через `concurrent.futures.ThreadPoolExecutor`.
2. **Веб-сервер**: REST API развёрнуто на базе стандартного `http.server.ThreadingHTTPServer`. Сервер обрабатывает входящие HTTP-запросы синхронно и отдаёт JSON-ответы.
3. **CLI-интерфейс**: Разработан с использованием модуля `argparse`, предоставляя команды для запуска сервера (`serve`), выполнения разового расчёта (`assess`), деморежима (`demo`) и воспроизведения старых прогонов (`replay`).
4. **Хранение данных**: Встроенная СУБД **SQLite** (`sqlite3`) используется для кеширования ответов от провайдеров (snapshots) и сохранения результатов каждого расчёта (runs). Режим `WAL` (Write-Ahead Logging) включён для оптимизации параллельного чтения/записи.
5. **Чистые вычисления**: Вся сложная логика пересечений интервалов (DateTime), агрегации событий и оценки окон вынесена в `core.py`. Эти функции являются чистыми (pure functions), не выполняют I/O операций и полностью покрыты юнит-тестами.

### тесты

В проекте реализовано 22 автоматизированных юнит- и интеграционных теста с использованием встроенного модуля `unittest`. Они разбиты на два основных файла, расположенных в `src/test/events/`:

1. **`test_service.py` (Основы бизнес-логики и изоляция данных)**
   Фокусируется на проверке чистого ядра (`core.py`), менеджера хранилища и пограничных состояний времени:
   * **Вычисления интервалов**: Убеждается, что пересекающиеся события не дублируют итоговое время опасности (`test_no_double_count_overlap`), проверяет полуоткрытые интервалы (`test_half_open_boundaries`) и обработку событий без известного окончания (`test_unknown_end_not_invented`).
   * **Машина времени (`as_of`)**: Гарантирует, что алгоритм не заглядывает в будущее, игнорируя новые данные при реконструкции исторических моментов (`test_asof_excludes_newly_downloaded_old_catalog`).
   * **Логика парсеров**: Проверяет правильность отсева (например, фильтрацию объектов SOCRATES, учёт разрывов в данных GOES, сохранение шкалы TDB для астероидов JPL).
   * **Устойчивость кеша**: Эмулирует падение сети (`patch` для `urlopen`), проверяя, что система отдаёт устаревшие снимки со статусом `stale`, а не обрушивает выполнение (`test_cache_cutoff_and_failed_network`).

2. **`test_extended.py` (Интеграционный слой и API)**
   Покрывает оркестрацию, адаптеры и HTTP-коммуникации:
   * **HTTP REST API**: Поднимает реальный сервер в фоновом потоке, тестирует эндпоинты `/health` и `/assess`, проверяет валидацию длины и структуры JSON-тела (отдача `400 Bad Request`).
   * **Адаптеры**: Тестирует парсинг свободных текстовых полей (выделение дат из алертов NOAA), проверку статусов отмены и парсинг различных каталогов DONKI (FLR, GST).
   * **Оркестратор (`service.collect`)**: Убеждается, что принудительно отключённые источники (`disabled`) и провайдеры с сетевыми ошибками правильно маркируются в итоговой сводке и не прерывают сбор остальных данных.
   * **Конфигурация**: Проверяет отбраковку невалидных конфигурационных JSON-файлов.

**Как это работает:** 
Во время тестов внешние сетевые вызовы либо заглушаются через `unittest.mock.patch` (и моки базы данных), либо обрабатывают локальные фикстуры, что обеспечивает быстрое (до 1 секунды) и детерминированное выполнение всего набора. Для работы с SQLite-файлом во временной директории применяется безопасное закрытие транзакций (`contextlib.closing`), чтобы тесты не блокировали файлы на Windows.

**Запуск тестов:**
Выполняется из корневой директории командой:
```bash
python -m unittest discover -s src -t . -v
```

## Injection

- Описание API: http://127.0.0.1:8000/docs
- Проверка: http://127.0.0.1:8000/health
- Деморежим не требует сети. Все его данные явно синтетические.
- Рабочие режимы не подставляют демоданные при ошибке источника.

Текущая обстановка и варианты начала в ближайшие 6 часов:

```bash
python3 app.py assess --duration-hours 6 --search-hours 6 --output current.json
```

В этой команде начало автоматически равно текущему времени UTC. Получение нескольких источников может занимать около минуты. Результат сохраняется в JSON, исходные ответы и расчёты — в `data/events/eva.sqlite3`.

HTTP-запрос (замените дату на нужную):

```bash
curl -X POST http://127.0.0.1:8000/assess \
  -H 'Content-Type: application/json' \
  -d '{"start":"2024-05-10T12:00:00Z","duration_hours":6,"search_hours":6,"step_minutes":60,"mode":"reconstruction"}'
```

Ответ содержит `run_id`. Сохранённый результат доступен по `/runs/{run_id}`, исходный ответ поставщика — по `/snapshots/{snapshot_id}`. API выполняет запрос синхронно; отдельных фоновых заданий, процентов готовности и UI в этой версии нет. Сервер по умолчанию слушает localhost; публичный production-деплой требует отдельного сервера/прокси и контроля доступа.

## Метрики на выходе

Дополнительно возвращаются `events`, `context`, `sources`, `coverage_intervals`, параметры, версия алгоритма и исходные ссылки. Числа здесь характеризуют события; сервис не ограничивается выдачей сырых Kp/потоков.

Пример вычисления: прогноз CME действует 12:00–15:00, прогноз Kp ≥ 5 действует в тот же период. Для окна 12:00–18:00 пересечение геомагнитных сигналов составляет **180 минут, а не 360**. Сближение в 13:30 с плановым буфером ±30 минут даёт отдельные **60 минут** для механизма столкновений. Буфер — правило команды для внимания аналитика, не физическая длительность столкновения и не доверительный интервал TCA.

Интервалы полуоткрытые `[start, end)`. Мгновенное событие на правой границе относится к следующему окну. Дубли версии одной записи удаляются. Явные связи DONKI объединяются транзитивно. Между разными поставщиками автоматического отождествления одного события нет. Прогнозы разных запусков ENLIL могут быть альтернативами: объединение интервалов — консервативный набор возможных периодов, не сумма вероятностей. Число их записей не следует подавать в ML как число независимых CME.

`event_burden_frontier_indices` — варианты, не уступающие другим по всем длительностям объединённых интервалов. Это предварительное сравнение сигналов. Неизвестные окончания, полнота, геометрия и неопределённость времени не превращаются в ноль риска. `recommendation.preferred_window` остаётся `null`: этот компонент не имеет локальной модели воздействия для допуска/окончательной рекомендации. Модель выбора вашего проекта должна получать вектор факторов вместе с признаками неизвестности.

## Время, наблюдения и прогноз

- Все пользовательские времена содержат часовой пояс; на выходе UTC.
- У события раздельно хранятся `start`, `end`, `published_at`, `fetched_at`.
- `basis` разделяет наблюдение, внешний прогноз, внешнюю оценку и расчёт команды.
- Для ENLIL `modelCompletionTime` сохраняется в `values`, но не выдаётся за публикацию. Наблюдаемые поздние исходы `ipsList` не участвуют в расчёте прогноза.
- Время астероидов JPL — **TDB**, а не UTC. Оно остаётся в `context` с явной шкалой. Даты запроса расширяются на сутки; контекст может содержать события вне окна. Сравнения астероидных времён с окном UTC нет.
- GOES: между соседними валидными отсчётами применяется удержание предыдущего значения; разрыв больше 1.5 штатного шага не заполняется. Невалидные/загрязнённые отсчёты исключаются. Продолжение после последнего измерения не прогнозируется. Пороговый эпизод не равен официальному определению начала/конца вспышки NOAA.
- Kp ≥ 5 — правило обнаружения геомагнитного события; Kp и GOES не переводятся в дозу космонавта.
- Неизвестное окончание SEP не заменяется выдуманными шестью часами. Каталожные сигналы старше начала окна могут остаться «возможно продолжающимися»; это повод запросить подтверждающие данные.

## История и воспроизводимость

```bash
python3 app.py assess --mode reconstruction \
  --start 2024-05-10T12:00:00Z --duration-hours 6 --search-hours 6 \
  --output history.json
```

Даты мая–июня 2024 года обрабатываются запросами DONKI/JPL по дате, а не заранее написанными ответами. Это **историческая реконструкция по текущим версиям архивных записей**. Она может содержать поздние уточнения. Современные NOAA rolling feeds и современный SOCRATES не подмешиваются в прошлое.

Строгое отсечение:

```bash
python3 app.py assess --mode as_of --as-of 2024-05-10T10:00:00Z \
  --start 2024-05-10T12:00:00Z --output asof.json
```

`as_of` использует только локальные снимки, реально сохранённые не позднее отсечения, и проверяет объявленное время публикации. Если таких снимков нет, возвращается недостаток данных. Скачанная сегодня запись с датой 2024 года не доказывает доступность именно этой версии в 2024 году. В комплекте **нет аутентифицированных снимков, собранных в мае–июне 2024 года**, поэтому обязательный по полному заданию проверяемый прогноз из прошлого эта версия ещё не закрывает. Нельзя менять `fetched_at` в базе ради получения результата.

```bash
python3 app.py assess --mode reconstruction --start 2024-05-10T12:00:00Z --offline
python3 app.py replay RUN_ID --output replayed.json
```

Offline требует точно совпадающих параметров URL. Replay повторно рассчитывает метрики из сохранённых нормализованных входов. Полные исходные тела, URL, заголовки и время получения сохраняются в SQLite отдельно; копируйте базу вместе с JSON для проверки парсеров. При миграции алгоритма сохраните предыдущую версию исходного кода. Рабочую базу переносите после остановки сервера или через SQLite backup API.

## Настройки, сбои и проверка

```bash
python3 app.py --config config.example.json serve
python3 -m unittest discover -s tests -v
```

`disabled_sources` содержит имена вроде `socrates`, `donki_MPC`, `noaa_alerts`. Параметры буфера и порогов вынесены в конфигурацию. Это исследовательские настройки; они не оптимизированы по исторической выборке.

Источник сообщает собственный статус. Ошибка загрузки возвращает старый снимок с `stale`, если он есть. Ошибка схемы — `unavailable`, а не пустой успешный список. Для свежести отличайте возраст скачивания и срок данных: свежескачанный Kp с истёкшими интервалами получает `out_of_date`. CSV SOCRATES не даёт достаточного основания доказать полное покрытие отчётного периода; его покрытие остаётся неизвестным. `MAX_PROB` сохраняется как максимальная оценка, не фактическая вероятность удара.

Проверки включают неизвестные окончания, границы интервалов, дублирующиеся воздействия, связи событий, утечку будущего, пропуски GOES, обе позиции МКС в CSV, отсутствие сети и кеш. Демонстрация не является научной валидацией. Сравнение с baseline, ложные предупреждения, орбитальная модель и оценка качества прогноза требуют следующего этапа.

## Что остаётся для полного задания

1. Исторические орбитальные элементы МКС, SGP4 и привязка хотя бы одного воздействия к траектории.
2. Локальная радиационная модель/геометрия, модель микрометеороидов и мелкого мусора.
